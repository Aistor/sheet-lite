# 12. 架构决策记录（ADR）

本文记录影响项目架构、技术选型和开发流程的关键决策。ADR 用于说明“为什么这样决定”，具体实现细节以对应技术文档和源码为准。

- 新增 ADR：遇到影响架构、技术路线、数据模型或开发流程的重大决策时新增。
- 更新 ADR：原决策被替代时，更新其状态并在新 ADR 中说明替代关系；不悄悄改写历史。
- 状态说明：`已决定` 表示当前采用；`待验证` 表示需通过原型或测试后确定；`已废弃` 表示不再适用于当前开发。

## ADR-001：自研网格核心

- 状态：已决定
- 决策：使用 Canvas 2D + DOM 编辑层，自研坐标、选区、命令和稀疏存储。
- 原因：保持核心实现可控，聚焦业务数据录入与轻量表格。
- 代价：键盘、剪贴板、合并单元格、公式和可访问性需要自行实现与测试。
- 复审：开发成本或功能复杂度超出预期时，重新评估局部引入成熟库。

## ADR-002：外围 UI 使用 Naive UI

- 状态：已决定
- 决策：Naive UI 用于工具栏、弹窗、表单和菜单，不承担核心网格渲染。
- 原因：降低外围 UI 开发成本，同时保持网格内核独立。

## ADR-003：MyBatis-Plus 与自定义批量 SQL 并用

- 状态：已决定
- 决策：常规 CRUD 使用 MyBatis-Plus；范围读取、批量 upsert、范围删除等性能敏感场景使用自定义 Mapper/XML/SQL。
- 原因：兼顾开发效率与批量操作性能。

## ADR-004：稀疏单元格存储

- 状态：已决定
- 决策：只持久化有内容、公式或显式样式的单元格，空单元格不落库。
- 原因：逻辑网格上限远大于实际填充数据。
- 注意：范围读取必须正确组合稀疏数据与默认值，明确空值语义。

## ADR-005：公式引擎通过适配层接入

- 状态：待原型验证
- 决策：先定义统一 `FormulaEngine` 接口，再评估 HyperFormula 等候选方案。
- 验证项：许可证、函数兼容性、内存占用、重算性能及公式引用重写。
- 注意：不能仅凭设置 `maxRows` 就认定引擎支持百万行复杂公式。

## ADR-006：首期不做实时协作

- 状态：已决定
- 决策：首期采用工作簿级 revision 和乐观并发控制，预留操作日志及协作适配层。
- 原因：实时协作会显著增加结构操作、撤销重做和公式依赖管理的复杂度。
- 复审：单人编辑与持久化闭环稳定后，再评估 Yjs/CRDT 或服务端操作日志。

## ADR-007：后端固定 JDK 21

- 状态：已决定
- 决策：开发、测试和构建统一使用 JDK 21，Maven 编译目标为 Java 21。
- 复审：升级 Java 基线时，通过新 ADR 记录，并验证全部依赖兼容性。

## ADR-008：前端统一使用 Yarn Classic 1.22.22

- 状态：已决定
- 决策：前端统一使用 Yarn Classic 1.22.22；在 `frontend/package.json` 中声明 `"packageManager": "yarn@1.22.22"`，提交 `yarn.lock`，安装依赖统一执行 `yarn install --frozen-lockfile`。
- 禁止：混用 npm、pnpm 或 Yarn Berry；不启用 Plug'n'Play。
- 原因：固定包管理器版本和锁文件行为，保持本地开发与 CI 的依赖解析一致。

## ADR-009：不采用 Docker 开发流程

- 状态：已决定
- 决策：当前项目不使用 Docker、Docker Compose 或 Dockerfile；MySQL 在本机或独立数据库环境运行。
- 复审：未来明确需要容器化时再单独评估。

## ADR-010：数据库结构与开发数据管理策略

- 状态：已决定
- 背景：项目当前采用个人开发模式，不涉及多人共同维护数据库或多环境自动部署。引入迁移框架、版本登记表和独立迁移执行器会增加维护成本；由 AI 助手按明确的安全规则管理本地数据库更符合当前开发流程。
- 决策：
  - 开发阶段由 AI 助手管理本地数据库结构和开发数据，可通过 MySQL 命令行或 Navicat 执行；Navicat 同时作为查看、导出和应急工具。
  - 不引入 Flyway、Liquibase，不使用 `schema_version`、schema 版本登记、迁移脚本校验和或迁移执行器。
  - `backend/src/main/resources/db/migration/V001__init_schema.sql` 仅作为初始数据库结构基线，不承担日常迁移职责；当前基线包含 11 张业务表，不包含 `schema_version`。
  - 数据库变更前检查当前结构并创建可恢复备份；变更后核对表、列、索引、约束和 COMMENT，并同步更新相关技术文档及初始结构基线（如适用）。
  - 任何破坏性操作，包括 `DROP`、`TRUNCATE`、`DELETE`、删除列或索引，必须先取得用户明确授权；执行前说明目标、影响范围及恢复方式。
  - 不在 Spring Boot 应用启动时自动创建、修改或删除数据库结构。
- 历史沿革：项目早期曾采用版本化 SQL、`schema_version` 登记表和独立迁移脚本；随后改为个人手动管理，再调整为由 AI 助手管理。历史迁移脚本已停用，`schema_version` 已从初始结构基线及本地数据库中移除。上述旧方案仅作为历史背景，不构成当前开发要求。
- 影响与代价：数据库结构与初始 SQL 基线可能发生偏离，需要依靠备份、结构核对和文档同步控制；AI 助手执行数据库操作必须遵守授权和验证要求。
- 复审条件：出现多人开发、多环境部署、CI/CD、生产环境或数据库审计要求时，重新评估数据库变更管理方案。


## ADR-011：后端使用本机 Maven 3.9.9，不使用 Maven Wrapper

- 状态：已决定
- 背景：项目采用个人本地开发模式，开发环境已安装并验证 Maven 3.9.9。仓库内维护 Maven Wrapper 脚本及配置目录会增加不必要的文件和下载步骤。
- 决策：
  - 后端统一使用 JDK 21 和本机安装的 Maven 3.9.9。
  - 仓库不保留 `.mvn/`、`mvnw`、`mvnw.cmd`，开发命令统一使用 `mvn`。
  - 开发者执行构建前通过 `java -version` 和 `mvn -version` 检查实际工具链版本。
  - 如未来引入 CI，CI 环境负责安装并固定 Maven 3.9.9，不依赖仓库内的 Wrapper。
- 原因：当前是个人开发项目，本机工具链已验证可用；减少仓库维护内容，同时通过文档和环境检查保持版本一致。
- 复审条件：出现多人协作、CI 环境无法稳定预装 Maven，或需要让新环境免安装 Maven 即可构建时，重新评估是否恢复 Wrapper。


## ADR-012：应用外壳与表格内核的交互契约

- 状态：已决定（UI-1 已实施）
- 背景：新增分组工具栏、编辑栏与品牌资源后，外壳组件需要稳定的数据与命令入口；若页面直接读写 Store，会绕过命令层并产生第二份活动单元格状态。
- 决策：
  - `AppHeader`、`FormatToolbar`、`FormulaBar` 放在 `frontend/src/components/`，只由 `pages/EditorPage.vue` 组合，不直接访问 `SparseCellStore`、`SparseStyleStore` 或命令管理器。
  - `SpreadsheetGrid` 通过 `active-change` 事件暴露活动单元格对象（地址、选区模式、`rawInput`、可编辑性），并提供 `applyInput`、`undo/redo` 与 `history-change` 供外壳调用。
  - 地址唯一展示位是编辑栏左侧名称框；编辑栏显示 `rawInput`，格式化展示由渲染层负责；提交走 `SET_CELL` 命令。
  - 图标统一使用 `@vicons/material` 的具名导入（Outlined），禁止整包引入。
  - 品牌资源保留原始静态/动画 logo；新增 `sheetlite-logo-mark.svg`（仅图案、无字标）用于页头与 favicon；原动画 logo 用于首次启动 splash，遵循 `prefers-reduced-motion`。
- 原因：保持 `core` 不依赖 Vue/DOM；外壳可独立测试；避免出现“顶栏地址”与“网格活动单元格”两份状态；控制包体与动画可访问性。
- 代价：`SpreadsheetGrid` 的公开面扩大，需要维护事件负载兼容；编辑栏与内联编辑需要约定互斥的提交顺序。
- 复审条件：引入多工作表标签、多行公式编辑器、协同编辑或移动端布局时，重新评估外壳与内核的边界。
- 关联规格：[13 应用外壳](13-ui-shell.md)。


## ADR-013：写操作幂等重放优先于 revision 冲突校验

- 状态：已决定
- 背景：写请求可能在服务端成功提交后因网络问题丢失响应。客户端使用原 `operationId`、`baseRevision` 重试时，工作簿 revision 已推进；若先校验 `baseRevision`，合法重试会被错误返回为 revision 冲突。
- 决策：在同一事务中锁定工作簿并完成身份、资源状态和写权限校验后，先查询 `(workbook_id, operation_id)`。若记录存在，比较规范化请求内容：一致则返回原 revision 和 `duplicate=true`；不一致则返回 `OPERATION_ID_REUSED`。只有记录不存在时才校验 `baseRevision` 并执行新写入。
- 安全约束：权限检查先于幂等结果返回，避免权限已撤销的调用者通过重放读取操作结果。
- 并发约束：同一工作簿的写事务先锁工作簿行；并发相同 operationId 请求串行化，后到请求应读取先到事务提交的日志记录。
- 影响：操作日志必须保存足以比较请求一致性的规范化内容；若未来引入独立请求摘要列，需核对实际 DDL 并同步 V001 初始结构基线。重放响应只承诺已持久化的 revision 和重复标志，不承诺未保存的完整响应体。
- 关联文档：[05 数据库与 MyBatis-Plus](05-database-mybatis-plus.md)、[08 API 与版本控制](08-api.md)。

## ADR-014：工作簿所有权以 owner_id 为唯一权威来源

- 状态：已决定
- 背景：`sl_workbook.owner_id` 与成员表中的 `OWNER` 记录若同时作为权限来源，可能因数据不一致而产生权限并集，导致已转移或已撤销的所有者身份继续生效。
- 决策：`sl_workbook.owner_id` 是唯一所有权事实来源；所有者权限由该字段派生。`sl_workbook_member` 只保存非所有者成员的 `EDITOR` / `VIEWER` 共享权限，应用不得写入或依赖 `OWNER` 成员记录。
- 所有权转移：必须在同一事务中更新 `owner_id` 和相关成员记录；原所有者转移后的角色必须由请求明确指定。
- 兼容约束：若当前物理表仍允许 `OWNER` 值，应用层仍不得使用；是否收紧数据库 CHECK/枚举需先检查真实 DDL，再更新初始结构基线。
- 关联文档：[05 数据库与 MyBatis-Plus](05-database-mybatis-plus.md)。
